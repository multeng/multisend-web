# TON Multisend — дизайн локального каркаса, этап 1А

Дата: 2026-10-27. Статус: frontend-подмножество согласовано пользователем поручением начать разработку; backend реализуется отдельно.

## Цель и результат

Поднять воспроизводимый локальный frontend и Go API, проверить их связь и подготовить проверки для дальнейшей разработки. Этот блок реализует этап 1А общей дорожной карты `F:/ton-multisend/PLAN.md`.

Результат для пользователя: адаптивная стартовая страница TON Multisend с понятным назначением сервиса и проверкой доступности API. Страница задаёт основу выбранного редактора B; рабочие списки и выплаты появятся в последующих блоках. Проверка состояния API не выдаётся за готовность выполнять выплаты.

## Подход и принятые решения

- Использовать ранее выбранные React + TypeScript + Vite, Radix Themes и CSS Modules; backend — Go `net/http`, отдельные репозитории.
- Статический frontend и общий Go API — выбранный подход. Next.js/SSR ранее рассмотрен и отвергнут пользователем для этого проекта; отдельный BFF не добавляется.
- В первом блоке Go API реализует только liveness/readiness. PostgreSQL, вход, TON Connect и отправка — следующие этапы, как уже определено дорожной картой.
- Технический выбор ассистента: разработка в существующей Windows-среде, npm через `npm.cmd`. Go при необходимости подготовить из официального дистрибутива с проверкой SHA-256; локальная распаковка может находиться в родительской `.tools/`, вне исходников репозиториев. Постоянный системный PATH без отдельной необходимости не менять.
- Репозитории сейчас не имеют первого коммита; Git worktree от существующего HEAD пока невозможен. Первое основание проекта создаётся в имеющихся пустых checkout, далее вопрос изоляции применяется к feature-веткам. Во время этого review Git не менялся.

## Инструменты

- Уже установлены Node.js 24.22.1 и npm 11.19.1.
- Кандидаты для закрепления при создании проекта, проверенные прямым запросом npm: React 19.3.1, Vite 8.3.5, Radix Themes 3.3.0. Metadata Vite допускает Node.js 24; peerDependencies Themes допускают React 19. Это проверка metadata, а не результат установки/сборки.
- Официальный список дистрибутивов Go на дату проверки содержит stable Go 1.27.3; выбрать windows-amd64 для текущей машины. Фактическую работоспособность проверить после установки.
- TypeScript, Vite plugin и средства проверок подобрать совместимыми, закрепить в lockfile. Команды CI используют те же версии. Обновление npm ради номера версии не требуется.

## Frontend

- Стартовая страница в выбранном светлом направлении синих акцентов; Radix Themes обеспечивает компоненты, собственные стили — CSS Modules.
- Показать название, назначение продукта, сообщение о текущем этапе разработки и блок состояния API с кнопкой повторной проверки. Индикатор запрашивает `/api/readyz` и различает проверку, готовность, HTTP 503 «ещё не готов» и ошибку связи/контракта. Не показывать неработающие действия реальной отправки.
- Разделять код страницы и небольшой клиент проверки состояния. Не переносить исходники демонстрационного макета в production как готовую платёжную логику.
- Vite слушает `127.0.0.1:5173`, `strictPort: true`; `/api` проксируется в `http://127.0.0.1:8080`. Адрес dev-proxy можно переопределить конфигурацией. Frontend обращается относительным путём, без отдельного CORS/BFF и без секретов в `VITE_*`.
- В этом блоке нет пользовательских списков, cookies входа или локального хранения личных данных. Отмена устаревшего запроса/размонтирование не должны давать ложное состояние или ошибку интерфейса.

## API и контракт

- `GET /api/healthz`: HTTP 200, JSON `{"status":"ok"}` — процесс обслуживает запросы.
- `GET /api/readyz`: HTTP 200, JSON `{"status":"ready"}` — завершена инициализация данного каркаса; БД/RPC зависимостей в нём пока нет. Для неготового состояния контракт — HTTP 503, JSON `{"status":"not_ready"}`. При завершении сначала снять readiness, затем инициировать graceful shutdown и дать активным запросам закончиться в пределах таймаута.
- Для JSON использовать `Content-Type: application/json; charset=utf-8`, для этих ответов `Cache-Control: no-store`. Неподдерживаемые методы возвращают 405; неизвестный путь — 404. HEAD обрабатывается стандартным HTTP-поведением без тела.
- Canonical OpenAPI находится в `multisend-api/api/openapi.yaml`, версия контракта `0.1.0`. Для двух проверок состояния frontend использует этот явно описанный JSON; генерация клиентских типов для предметного API остаётся в этапе 1Б. Сборка публичного frontend не требует чтения приватного репозитория.
- Адрес сервера задаётся через `LISTEN_ADDR`, default `127.0.0.1:8080`. Ошибка формата/занятый порт завершают запуск с понятным сообщением. Настроить таймауты HTTP и завершение по сигналу; никаких секретов, БД, ключей кошельков или фонового исполнителя выплат.

## Границы и структура

Предлагаемая структура фиксирует обязанности; подробные функции и тестовые шаги будут в плане реализации после согласования дизайна.

- `multisend-web`: package.json/lockfile, конфигурация Vite/TypeScript и проверок, `src/app/` для страницы, `src/api/` для HTTP-клиента, README, `.env.example`, `.gitignore`, workflow CI.
- `multisend-api`: `go.mod`, `cmd/api/` для запуска, `internal/config/` для конфигурации, `internal/httpapi/` для маршрутов и lifecycle, `api/openapi.yaml`, README, `.env.example`, `.gitignore`, workflow CI.
- README каждого репозитория содержит поддерживаемые версии, команды установки/запуска/проверок, порты и способ изменения конфигурации. Абсолютные пути текущего компьютера не используются в коде приложения.
- Доступность production, домен, платные сервисы, Docker, PostgreSQL, аутентификация, CSV-редактор, аналитика и реальные переводы в этот блок не входят. Сохранение безопасности и функциональности последующих этапов описано общей дорожной картой.

## Критерии приёмки

- По README запускаются оба приложения; пользователь видит доступность API и понятный отказ при выключенном backend. Ошибка backend не превращает страницу в пустой экран.
- Сборка frontend воспроизводима через `npm.cmd ci` и `npm.cmd run build`. Проверки типов, применимые тесты и линтер выполняются локально и описаны в CI.
- Go проходит `go test ./...`, `go vet ./...` и сборку. Проверены оба HTTP-контракта, неправильный метод/путь и ошибочная конфигурация запуска.
- Frontend корректно обрабатывает network error, не-200 и неподходящий JSON; порядок повторных запросов не подменяет последний результат устаревшим.
- На ширинах 360, 390, 768 и 1280 px нет горизонтального переполнения, кнопки доступны с клавиатуры и есть видимый фокус. Это локальная проверка каркаса; реальные телефоны/кошельки проверяются позже.
- Локальные проверки и подготовка workflow не считаются выполненным запуском GitHub Actions. До разрешённого push результат — «локальная реализация проверена; удалённый CI ожидает запуска». Полностью закрывать этап 1А в roadmap можно после успешного GitHub Actions и остальных критериев; разрешение на публикацию не предполагается из создания локального каркаса.
- Настройка и проверка одного блока не запускают автоматически следующий. Итог фиксируется в общей дорожной карте с фактическими командами и результатами.
