# Russian and English interface

The owner requested exactly Russian and English. Use a small typed React translation catalog and accessible header selector, without a new dependency, URL routes or backend changes. A full i18n framework was considered; there is no plural grammar/date/currency formatting feature requiring it in this block. Both approaches are valid; the builder chooses the smaller catalog for these two fixed locales. Source Russian messages serve as typed catalog IDs (gettext style), English translations are exhaustive; user-created content is never passed through the translator.

Detect a saved `ton-multisend.locale` value first, then the browser's primary language (ru -> Russian, en -> English, others -> English). Store only an explicit locale selection, catch blocked storage reads/writes. Locale updates document.lang, title/description and existing rendered messages without reload/remount of editor/auth/query clients. No recipient/name/amount/comment conversion; decimal point and CSV headers remain locale independent. Existing API contracts, network and wallet ownership checks stay unchanged.

Translate landing/status, authentication messages, drafts, recipient forms/dialogs, CSV errors, warnings, confirmation/save states, placeholders and accessible labels. Dynamic counts/record numbers use interpolation; stored errors remain translatable after changing language. TON Connect changes its UI language through the existing setOptions API without recreating/disconnecting the connector. Browser-native file/unload dialogs follow browser language; wallet-app UI follows wallet settings. Product content/name and sample CSV remain unchanged.
